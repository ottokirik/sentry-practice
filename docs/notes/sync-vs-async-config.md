# Конфигурация стенда: синхронно или после старта

Заметка к лабе 02b. Исходная ситуация на рабочем проекте: entrypoint
контейнера забирает конфигурацию с внутреннего сервиса и через `jq`
раскладывает её на статические JSON-файлы рядом со сборкой. Приложение
запрашивает их все уже после старта, даже те, которые можно было бы отдать
синхронно.

## Вопрос не «как», а «когда нужно значение»

Сравнивать способы для всего конфига сразу бессмысленно. Для каждого значения
вопрос один: **нужно ли знать его до первой строки кода приложения?**

- Да — мониторинг, окружение и стенд, базовый адрес API, флаги, от которых
  зависит первый экран.
- Нет — настройки отдельных фич, справочники, всё крупное, персональное или
  обновляемое без перезагрузки.

## Особенность инфраструктуры, которая меняет расклад

Главный недостаток синхронного скрипта: разбор HTML останавливается, пока
скрипт не загрузится. Если бы его отдавал медленный удалённый сервис, это был
бы серьёзный риск — зависший запрос означает пустую страницу.

Но в описанной схеме `config.js` — статический файл в том же поде, что и
`index.html`, и отдаёт его тот же веб-сервер. Если `index.html` дошёл до
браузера, `config.js` почти наверняка дойдёт тоже и за миллисекунды. Большая
часть этого недостатка здесь отпадает.

## Синхронный `<script src="./config.js">`

| Плюсы | Минусы |
|---|---|
| Значения известны до первой строки кода: Sentry, аналитика и флаги инициализируются сразу с правильными значениями, ошибки старта не теряются | Разбор HTML ждёт загрузки скрипта. Если запрос завис, страница пустая, и таймаут не в твоих руках |
| Нет состояния «конфиг ещё грузится»: чтение — обычная синхронная операция, без промисов через всё приложение и гонок «использовали до загрузки» | Нет управления ошибкой — ни повтора, ни экрана ошибки. Приложение должно само пережить отсутствие конфига |
| Флаги верны с первого рендера, интерфейс не мигает | Это код, а не данные. Генерировать его надо аккуратно (`tojson`), иначе ошибка генерации даёт `SyntaxError` — см. [разбор `jq`](render-config-jq.md) |
| Нет водопада запросов, см. ниже | Глобальная переменная: в тестах её надо подменять, в микрофронтендах возможен конфликт имён |
| | Нельзя сделать персональным или требующим авторизации |
| | Отдельный запрос на каждой загрузке страницы с `no-cache`. Сервис-воркер не должен его кешировать, а офлайн-старт останется без конфига |

## Запрос после старта

| Плюсы | Минусы |
|---|---|
| Не блокирует первую отрисовку, можно показать каркас страницы | **Водопад:** HTML → бандл → выполнение бандла → запрос конфига → только потом запросы к API. Каждый этап ждёт предыдущий |
| Таймауты, повторы, запасное значение и экран ошибки — под контролем | Состояния загрузки и гонки во всём коде, который зависит от конфига |
| Данные, а не код | Мониторинг и флаги инициализируются поздно: ошибки старта теряются или получают неправильное окружение, флаги переключаются уже после первого рендера |
| Можно сделать персональным и перечитывать без перезагрузки | |

## Как бы я сделал

### 1. Разделить конфиг на две части

**Стартовая часть** — синхронная и маленькая: окружение, стенд, настройки
мониторинга, базовый адрес API, флаги первого экрана.

**Всё остальное** — асинхронное, как сейчас.

Переносить в синхронный скрипт всё подряд не стоит. Он грузится на каждой
загрузке страницы до первого рендера, и чем он больше, тем дороже эта
задержка обходится всем пользователям.

### 2. Стартовую часть — как в лабе 02b

- `config.js` с белым списком полей через `jq` — одна дополнительная строка в
  entrypoint;
- `Cache-Control: no-cache` на `config.js`;
- исключить `config.js` из прекеша сервис-воркера;
- явное запасное значение в коде (`?? "unconfigured"`) и `?.` на каждом уровне
  вложенности;
- алерт в Sentry на окружение `unconfigured` — это сломанная раскатка.

### 3. Альтернатива: JSON прямо в `index.html`

Entrypoint встраивает стартовый конфиг в `index.html`, а приложение читает его
синхронно:

```html
<script type="application/json" id="app-config">{"environment":"staging",...}</script>
```

```ts
const config = JSON.parse(
  document.getElementById("app-config")?.textContent ?? "{}",
);
```

Плюсы: нет лишнего запроса вовсе, и это данные, а не исполняемый код —
ошибка генерации не превращается в `SyntaxError` на весь скрипт.

Цена:

- entrypoint меняет `index.html`, то есть артефакт на стенде уже не побайтово
  тот, что тестировали;
- `index.html` тоже нельзя кешировать сервис-воркером, иначе конфиг застынет;
- **обязательно экранировать `<`**. `tojson` этого не делает, и значение с
  `</script>` закроет тег посреди JSON.

Проверенная команда:

```bash
jq -r '{environment, stand, sentry} | tojson | gsub("<"; "\\u003c")' stand-config.json
```

На входе `"environment": "stag</script><script>alert(1)</script>"` она даёт

```
{"environment":"stag</script><script>alert(1)</script>",...}
```

— во встроенном теге остаётся ровно один закрывающий `</script>`, а
`JSON.parse` возвращает исходную строку.

Для вашей схемы я бы всё же выбрал отдельный `config.js`: артефакт остаётся
неизменным, а entrypoint только добавляет файлы, ничего не переписывая.

### 4. Асинхронную часть оставить, но убрать водопад

Семантика прежняя, запрос просто начинается раньше:

```html
<link rel="preload" href="./config/app.json" as="fetch" crossorigin>
```

Загрузка стартует во время разбора HTML, а не после выполнения бандла. Когда
приложение потом вызовет `fetch("./config/app.json")`, браузер отдаст уже
загруженный ответ.

**`crossorigin` здесь обязателен, даже для своего домена.** Проверено в
Chromium: страница с `preload` и последующим `fetch`, сервер отдаёт
`Cache-Control: no-store`.

| Вариант | Запросов к `app.json` |
|---|---|
| с `crossorigin` | 1 |
| без `crossorigin` | 2 |

Причина — `fetch()` по умолчанию делает запрос в режиме CORS, а `preload` без
`crossorigin` — нет. У запросов разный режим, и браузер не считает их
одинаковыми.

Коварная деталь: при обычном кешировании оба варианта показали по одному
запросу — второй `fetch` без `crossorigin` просто взял ответ из HTTP-кеша, и
проблема не видна. Проявляется она ровно тогда, когда конфиг отдают с
`no-cache` или `no-store`, то есть как раз для конфигов.

И ещё: запрашивать конфиг в одном модуле на старте приложения, а не глубоко в
компонентах — с таймаутом, повтором, типизированным результатом и отправкой
ошибки в Sentry.

### 5. Измерить до и после

В лабе 06 подключается `browserTracingIntegration()`. Транзакция загрузки
страницы показывает запросы отдельными спанами с таймингами, так что водопад
конфигов будет виден прямо в Sentry — на реальных пользователях, а не на
локальной машине. Сними картину до изменений и после.
