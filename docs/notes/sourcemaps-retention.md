# Хранение source maps: сколько живут в Sentry и как не остаться без них

Заметка к лабам 04–07. Всё, что помечено «проверено», выполнено руками на
этом проекте (Excalidraw, `@sentry/vite-plugin` 5.4.0, `sentry-cli` 2.58.6,
организация в регионе `de.sentry.io`). В конце — список того, что проверить
не удалось.

## Коротко

- **Бесконечно карты в Sentry не копятся.** Бандлы с Debug ID удаляются
  после 90 дней без использования. Отдельная чистка не нужна.
- **Настоящий риск в обратном:** стабильная версия, которая 90 дней работает
  без ошибок, теряет карты, и первая же ошибка после этого придёт
  нечитаемой. Залить карты задним числом для неё уже не поможет.
- **Храни карты у себя** — но не просто `.map` из сборки: карты, сохранённые
  после работы плагина, потом не сопоставятся с кодом. Ниже два рабочих
  способа.

## Что пишет документация

Срок хранения:

> Artifacts containing Debug IDs are retained for 90 days using a
> time-to-idle expiration mechanism. They are kept as long as they are
> actively used for event processing and are eligible for deletion if not
> used for 90 days.

Отсчёт идёт не от заливки, а от **последнего использования**: пока по бандлу
расшифровываются события, он живёт.

Поздняя заливка:

> If artifacts are uploaded after an error is captured, Sentry will not
> retroactively apply source annotations to those past errors; only new
> errors will be affected.

## Чем опасен срок «без использования»

Модель «одна сборка на много стендов» делает версии долгоживущими: артефакт
может месяцами стоять на проде. Хорошая версия почти не шлёт ошибок и поэтому
почти не «использует» свои карты.

Сценарий:

1. Версия выкачена в январе, ошибок почти нет.
2. В апреле бандл удаляется: 90 дней без событий.
3. В мае случается редкая ошибка. Стектрейс нечитаемый.
4. Карты заливаются заново — но это событие уже обработано и останется
   нечитаемым. Расшифруются только следующие.

Защититься от шага 4 нельзя, можно только не допустить шага 2 или быстро
вернуть карты перед следующей ошибкой. Для этого карты нужны у тебя.

## Почему нельзя просто сохранить `.map` из сборки

Проверено. Плагин вшивает Debug ID в код так:

| Где | Что лежит в `excalidraw-app/build` |
|---|---|
| JS | вставка с `sentry-dbid-71180f51-…` — её читает SDK в браузере |
| JS, комментарий `//# debugId=` | **нет** |
| `.map`, поле `debug_id` | **нет** |

Комментарий и поле плагин дописывает только в копии во временном каталоге,
из которого идёт заливка, и этот каталог потом удаляется.

Если сохранить сырые карты и позже прогнать их через `sentry-cli`, CLI
вычислит **свой** Debug ID. Для главного чанка он получился `5c4fa849-…`
вместо `71180f51-…`, вшитого плагином. Карты уедут в Sentry, но с кодом на
стендах не сопоставятся — и узнаешь ты об этом только по нечитаемому
стектрейсу.

## Способ 1: заливка через `sentry-cli` и архив карт

Плагин для заливки не используется. Каждый шаг проверен.

### При сборке

```bash
# 1. сборка со sourcemap: "hidden", без sentryVitePlugin
yarn workspace excalidraw-app build:artifact

# 2. вшить Debug ID и в JS, и в карты — одинаковый
sentry-cli sourcemaps inject excalidraw-app/build

# 3. сохранить карты в закрытый архив ДО удаления
(cd excalidraw-app/build && find . -name '*.map' | cpio -pdm "$MAPS_ARCHIVE")

# 4. залить
sentry-cli sourcemaps upload --release "$VITE_APP_RELEASE" excalidraw-app/build

# 5. убрать карты из того, что поедет на стенды
find excalidraw-app/build -name '*.map' -delete
```

Результат проверки:

- после `inject` в главном чанке комментарий `//# debugId=4d7f93ca-…` и поле
  `debug_id` в карте совпадают;
- в архиве 114 карт, в деплоимом артефакте 0;
- **событие из этой сборки в браузере пришло с `debug_id` `4d7f93ca-…`** для
  упавшего файла — SDK использует именно вшитый CLI идентификатор.

### Восстановление

Артефакт у вас и так хранится. Карты кладутся обратно рядом с кодом, и
заливка повторяется:

```bash
cp -r "$ARTIFACT"/. restore/
cp -r "$MAPS_ARCHIVE"/. restore/
sentry-cli sourcemaps upload --release "$RELEASE" restore
```

Проверено: Bundle ID получился тот же, что при исходной заливке, а в отчёте
тот же Debug ID. Если бандл в Sentry ещё есть, CLI ответит
`Nothing to upload, all files are on the server` — данные повторно не
передаются.

### Цена

- Архив карт — это **исходный код**. Доступ к нему закрывается так же, как к
  репозиторию, а не как к артефакту для стендов.
- Хранить карты нужно, пока версия может работать хоть на одном стенде.
- Вместо одной опции плагина — пять строк в CI. Проверку «в артефакте ноль
  карт» из лабы 07 оставь: теперь она страхует шаг 5.

## Способ 2: воспроизводимая пересборка

Ничего не хранить, а при необходимости пересобрать тот же коммит — плагин
вшьёт те же Debug ID и зальёт заново.

Проверено: три сборки одного коммита дали одинаковые имена чанков, а имя
чанка — хеш его содержимого, включая вставку с Debug ID. Идентификатор у
плагина вычисляется из содержимого, а не случайно.

Но воспроизводимость хрупкая. Одинаковыми должны быть:

- коммит и `yarn.lock` (`yarn install --frozen-lockfile`);
- версия Node и образ CI;
- **все переменные, попадающие в бандл**: `VITE_APP_RELEASE`,
  `VITE_SENTRY_DSN` и любые другие `VITE_*`.

Любое расхождение даёт другие Debug ID, и заливка молча становится
бесполезной. Поэтому перед тем как полагаться на пересборку, сравни имена
чанков с тем, что стоит на стенде:

```bash
ls excalidraw-app/build/assets/index-*.js
curl -s https://<стенд>/ | grep -o 'assets/index-[^"]*\.js'
```

Не совпали — пересборка не поможет.

Я бы использовал этот способ как запасной, а основным — архив.

## Когда заливать повторно

- **При каждой выкатке на прод** — дёшево: если бандл жив, данные не
  передаются. Если успел удалиться — вернётся до того, как придёт ошибка.
- **Перед разбором инцидента** на старой версии — если стектрейс уже пришёл
  нечитаемым, следующий будет читаемым.
- **По расписанию для версий, которые ещё стоят на стендах**, если между
  выкатками бывают паузы больше 90 дней.

## Как проверить, что карты для версии в Sentry есть

Поиск по Debug ID доступен с тем же токеном `org:ci`, что и для заливки.
Проверено:

```bash
ID=$(grep -o 'sentry-dbid-[a-f0-9-]*' excalidraw-app/build/assets/index-*.js | head -1 | cut -c13-)
curl -s -H "Authorization: Bearer $SENTRY_AUTH_TOKEN" \
  "https://de.sentry.io/api/0/projects/<org>/<project>/artifact-lookup/?debug_id=$ID"
```

Для сборки через `sentry-cli` Debug ID берётся из комментария
`//# debugId=` в конце файла.

Непустой массив — бандл есть, `[]` — нет. Адрес региона берётся из DSN
(`ingest.de.sentry.io` → `de.sentry.io`).

## Грабли, пойманные при проверке

- **Задержка индексации.** Сразу после успешной заливки поиск вернул `[]`,
  через минуту — бандл нашёлся. CLI честно пишет
  `processing pending on server`. Проверка в CI сразу после заливки дала бы
  ложную тревогу — нужен повтор с ожиданием.
- **Сбой DNS посреди заливки.** `sentry-cli` падал с
  `Could not resolve host: de.sentry.io`, а плагин показывал только
  `failed with exit code 1`. Настоящая причина видна с
  `SENTRY_LOG_LEVEL=info`. `errorHandler` из лабы 04 здесь и спасает: без
  него сборка была бы зелёной, а карт не было бы нигде.

## Удаление

Специально удалять ничего не нужно. Вручную — **Settings → Projects →
excalidraw-lab → Source Maps**, в основном при утечке: например, если в
карты попали секреты из исходников.

## Что проверить не удалось

- Продлевает ли повторная заливка уже существующего бандла срок хранения.
  Ответ `Nothing to upload` этого не показывает. Поэтому основная защита —
  архив, а не надежда на повторную заливку.
- Сам срок в 90 дней — взят из документации, дождаться удаления в рамках
  практикума нельзя.
