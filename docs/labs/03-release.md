# Лаба 03. Релизы

**~15 минут**

## Цель

Научиться помечать сборки версией — и понять, для чего этот механизм нужен
на самом деле.

## Теория на пять строк

`release` — строка-метка сборки. Sentry использует её, чтобы:

- показать, **в какой версии ошибка появилась впервые** и не вернулась ли она
  после того, как её починили (регрессия);
- связать событие с коммитами и подсветить **подозреваемый коммит**
  (suspect commits) — это будет в лабе 07;
- считать **release health**: долю сессий без падений в каждой версии.

### Чего release НЕ делает

Почти во всех статьях по Sentry написано, что `release` в SDK обязан совпадать
с релизом, под которым залиты source maps, иначе стектрейс не расшифруется.
**Это устарело.** Сейчас связь бандла и карты держится на **Debug ID** —
уникальном идентификаторе, который сборочный плагин вшивает и в JS-файл, и в
`.map`. Документация Sentry говорит прямо:

> Because debug IDs will generally change across releases if the file content
> is changed, **creating a release is no longer required**.

Более того, там же есть предупреждение: привязка загрузки к `release`/`dist`
делает процесс *строже* и «may lead to your code not being unminified».

Практический вывод: релизы ставим ради регрессий и suspect commits, а
расшифровку стектрейсов доверяем Debug ID. Если в лабе 05 что-то не
расшифруется — искать причину надо не в несовпадении релизов.

## Задание

### 1. Прокинь версию в сборку

Заведи переменную `VITE_APP_RELEASE` и заполняй её на этапе сборки коротким
хешем коммита. Тип для неё уже объявлен в `vite-env.d.ts` — он там с самого
начала.

Формат имени релиза свободный, но Sentry лучше распознаёт вид
`имя-пакета@версия`. Возьми `excalidraw-lab@<хеш>`.

### 2. Отдай её SDK

Добавь `release` в `Sentry.init`.

<details>
<summary>Эталон</summary>

`excalidraw-app/package.json`:

```json
"build:staging": "VITE_APP_RELEASE=${VITE_APP_RELEASE:-excalidraw-lab@$(git rev-parse --short HEAD)} vite build --mode staging",
"build:production": "VITE_APP_RELEASE=${VITE_APP_RELEASE:-excalidraw-lab@$(git rev-parse --short HEAD)} vite build --mode production",
```

Конструкция `${ПЕРЕМЕННАЯ:-значение}` означает «взять уже заданное значение, а
если его нет — подставить это». Локально переменной нет, и релиз соберётся из
хеша коммита. В лабе 07 её задаст CI (там релиз прода берётся из имени тега), и
скрипт это значение уважит, а не затрёт.

`excalidraw-app/sentry.ts`:

```ts
Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.MODE,
  enabled:
    import.meta.env.MODE !== "development" ||
    import.meta.env.VITE_SENTRY_FORCE_ENABLE === "true",

  // Метка версии: регрессии, suspect commits, release health.
  // На расшифровку стектрейсов НЕ влияет — этим занимаются Debug ID.
  release: import.meta.env.VITE_APP_RELEASE,
});
```

</details>

> **Про Windows.** Подстановка `$(git rev-parse ...)` — синтаксис POSIX-шелла.
> На Windows без Git Bash скрипт не отработает; там пришлось бы вычислять хеш
> в отдельном node-скрипте, как Excalidraw делает в `scripts/build-version.js`.

## Проверка

```bash
yarn workspace excalidraw-app build:staging
npx http-server excalidraw-app/build -p 5001 --silent
```

В шапке панели-детонатора должно появиться `release: excalidraw-lab@a1b2c3d`
вместо `(не задан)`.

Жми детонатор 1, открой событие в Sentry. В правой колонке, в блоке тегов,
будет `release`. Кликнув по нему, попадёшь на страницу релиза — пока пустую:
коммиты мы к нему привяжем в лабе 07.

## Осторожно: грязное дерево

`git rev-parse HEAD` возвращает хеш последнего коммита и ничего не знает про
несохранённые правки. Собрал с изменениями в рабочей копии — получил релиз,
который врёт: под этим хешем в репозитории лежит другой код.

Локально с этим живут, в CI проблемы нет вовсе — там дерево всегда чистое.
Проверить себя можно так:

```bash
git status --porcelain | head
```

Пусто — релизу можно верить.

## Что должно сломаться, если сделать неправильно

| Симптом | Причина |
|---|---|
| `release: (не задан)` в панели | Переменная не попала в сборку: собрал напрямую `vite build`, минуя скрипт |
| В теге релиза строка `$(git rev-parse --short HEAD)` целиком | Скрипт выполнился не в POSIX-шелле |
| Релиз есть, но страница релиза пустая | Так и должно быть. Коммиты привяжем в лабе 07 |
