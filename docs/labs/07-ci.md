# Лаба 07. CI: собрать один раз, раскатить на стенды

**~60 минут**

## Цель

Построить пайплайн, в котором артефакт собирается один раз и без изменений
уезжает на staging, а после ручного подтверждения — на прод. Карты заливаются
через `sentry-cli` и сохраняются в архив, из которого их можно вернуть в
Sentry. Токен живёт только в секретах CI.

## Теория

### Форма пайплайна

```
build
  ├ сборка артефакта
  ├ sentry-cli inject ─► архив sentry-bundle (код + карты)
  ├ релиз, заливка карт, коммиты
  ├ удаление карт ─► артефакт excalidraw-app (без карт)
  └ проверка: карты этого кода есть в Sentry
        │
        ▼
deploy staging-01 ──► [подтверждение] ──► deploy production-01
  ├ config.js стенда                        ├ повторная заливка карт из архива
  ├ публикация                              ├ config.js стенда, публикация
  └ deploy в Sentry                         └ deploy в Sentry

restore-sourcemaps (вручную): архив из любого прогона ─► заливка в Sentry
```

### Почему заливка больше не через плагин

Плагин из лабы 04 вшивает Debug ID только в JS. В `.map`, которые остаются в
сборке, идентификатора нет, а комментарий и поле плагин дописывает лишь в
копии во временном каталоге. Если сохранить такие карты и позже залить через
`sentry-cli`, CLI вычислит **другой** Debug ID, и карты не сопоставятся с кодом
на стендах.

Зачем вообще хранить карты у себя: Sentry удаляет бандл после 90 дней без
использования, а стабильная версия может столько проработать без ошибок.
Подробный разбор — в
[docs/notes/sourcemaps-retention.md](../notes/sourcemaps-retention.md).

`sentry-cli sourcemaps inject` пишет один и тот же Debug ID и в JS
(комментарий `//# debugId=` и вставка для SDK), и в карту (поле `debugId`).
Архив, сделанный после этого шага, заливается повторно без пересборки.

Проверено на этом проекте: после `inject` идентификаторы в JS и карте
совпадают; SDK в браузере отправляет именно этот ID; повторная заливка из
архива даёт тот же Bundle ID.

### Релиз и deploy — разные вещи

- **Релиз** — версия кода. Создаётся при сборке, один на артефакт.
- **Deploy** — факт выкатки релиза в окружение в определённый момент. Их
  столько, сколько было раскаток.

На странице релиза в Sentry видно, куда и когда его выкатывали. Регистрирует
deploy job раскатки: при сборке ещё неизвестно, куда артефакт поедет.

### Где хранить архив — и чем плох GitHub для рабочего проекта

В практикуме архив — артефакт workflow `sentry-bundle`. У этого решения два
ограничения, оба из документации GitHub:

- **Срок хранения в публичном репозитории — не больше 90 дней**, в приватном —
  до 400. Отсчёт идёт от создания, а не от использования. Версия, которая
  стоит на проде дольше, переживёт свой архив.
- **«People who are signed into GitHub and have read access to a repository
  can download workflow artifacts».** В публичном репозитории доступ на
  чтение есть у всех, так что архив с картами может скачать любой.

Для практикума это приемлемо: репозиторий и так публичный, исходники открыты.
На рабочем проекте архив карт — это исходный код: закрытое хранилище, доступ
как к репозиторию, срок — пока версия стоит хоть на одном стенде.

### Как это соотносится с рабочим проектом

| В практикуме | На рабочем проекте |
|---|---|
| job `deploy-*` | выкатка контейнера в под |
| `deploy/render-config.sh` в job | entrypoint контейнера |
| подкаталог стенда на Pages | под стенда |
| `deploy/stands/*.json` | внутренний сервис конфигурации |
| артефакт `sentry-bundle` | закрытое хранилище карт |

## Что уже есть в репозитории

- `deploy/publish-pages.sh <каталог> <стенд>` — публикует стенд в ветку
  `gh-pages`: заменяет только подкаталог этого стенда, остальные не трогает.
- `deploy/serve-stand.sh` удаляет `.map` из копии стенда. Без плагина
  локальная сборка карты больше не удаляет, а на стенд они попадать не должны.

Схемы релиза, deploy и того, откуда берётся каждая переменная, — в
[docs/notes/ci-release-deploy.md](../notes/ci-release-deploy.md).

## Задание

### 1. Заведи репозиторий и залей код

```bash
gh repo create sentry-practice --public --source=. --remote=origin --push
```

### 2. Секрет и переменная

```bash
gh secret set SENTRY_AUTH_TOKEN
gh variable set SENTRY_ORG --body "<слаг организации>"
```

Токен — секрет: GitHub маскирует его в логах и не показывает после записи.
Слаг организации секретом не является, поэтому это обычная переменная.

### 3. Разберись с путями — тут ловушка

Pages отдаёт сайт с `https://<логин>.github.io/sentry-practice/`, а стенды
будут жить глубже — в `staging-01/` и `production-01/`. Сборка Vite по
умолчанию рассчитана на корень домена, и по такому адресу все ассеты уйдут в
404.

Напрашивается `base: "/sentry-practice/staging-01/"`. **Так делать не надо**,
и дело даже не в том, что сборка одна на все стенды. Excalidraw подставляет
путь ассета в адрес своего CDN шрифтов, срезая ведущий слэш, и получается:

```
https://excalidraw.nyc3.cdn.digitaloceanspaces.com/oss/sentry-practice/fonts/... → 403
```

Рабочий вариант — **относительный** `base`: ассеты адресуются от текущего
каталога, и одна сборка работает на любой глубине. В
`excalidraw-app/package.json` не зря стоит `"homepage": "."` — авторы имели в
виду ровно это, просто Vite, в отличие от CRA, это поле не читает.

Добавь `base` в `excalidraw-app/vite.config.mts`.

### 4. Убери плагин заливки

В `excalidraw-app/vite.config.mts` удали `sentryVitePlugin({...})` и его
импорт. Остальное из лаб 04 и 05 оставь: `sourcemap: "hidden"` и
`workbox: { sourcemap: false }` по-прежнему нужны.

```bash
yarn workspace excalidraw-app remove @sentry/vite-plugin
```

Урок `errorHandler` из лабы 04 никуда не делся, он просто решается иначе:
`sentry-cli` при ошибке завершается с ненулевым кодом, а шаг workflow по
умолчанию выполняется с `set -e` и останавливается на первой упавшей команде.
Сборка не станет зелёной, если заливка не прошла. Одна оговорка из
документации GitHub: `pipefail` по умолчанию не включён, поэтому в шагах с
конвейером `curl … | jq` его нужно включить самому.

### 5. Опиши процедуру для Sentry в job `build`

#### Что раньше делал плагин

В лабе 04 всё происходило внутри одной команды `vite build`: плагин вшивал
Debug ID, заливал карты и удалял их. Три действия, одна непрозрачная команда.

Теперь эти действия выполняются отдельными шагами. Причина одна: между
«вшить ID» и «удалить карты» нужна пауза, чтобы **сохранить копию сборки с
картами**. Плагин такой паузы не давал.

#### Что происходит с каталогом сборки

Все шаги работают с одним каталогом `excalidraw-app/build`. Удобнее всего
следить, что в нём лежит после каждого шага:

```
                              в excalidraw-app/build
после сборки                  index.js         index.js.map
1. вшить Debug ID             index.js [ID]    index.js.map [ID]
2. архив sentry-bundle        ── копия этого ───────────────────┐
3. релиз и заливка            ── то же уезжает в Sentry         │
4. удалить карты              index.js [ID]                     │
5. проверка в Sentry          «есть карта для [ID]?»            │
6. артефакт excalidraw-app    ── копия этого ──┐                │
                                               ▼                ▼
                                    на стенды (без карт)   хранится на случай
                                                           повторной заливки
```

`[ID]` в обоих артефактах один и тот же: JS-файлы в них побайтово одинаковые.
Поэтому карты из архива подходят к коду на стендах.

#### Шаги по порядку

**1. Вшить Debug ID.**

```bash
sentry-cli sourcemaps inject excalidraw-app/build
```

CLI записывает одинаковый идентификатор в каждый JS-файл и в его карту — как
один номер на замке и на ключе. В конце JS появляется `//# debugId=…`, в карте —
поле `debugId`. По этому номеру Sentry потом найдёт карту для упавшего файла.

**2. Сохранить архив `sentry-bundle`** — весь каталог сборки, пока карты ещё
в нём (`actions/upload-artifact`). Именно здесь, до заливки: если заливка
упадёт, архив уже будет, и её можно повторить.

**3. Создать релиз и залить карты.** Четыре команды:

| Команда | Что делает |
|---|---|
| `releases new "$RELEASE"` | заводит в Sentry карточку версии |
| `sourcemaps upload --release "$RELEASE" --wait excalidraw-app/build` | отправляет JS и карты и ждёт, пока Sentry их обработает |
| `releases set-commits "$RELEASE" --auto --ignore-missing` | прикрепляет к версии список коммитов |
| `releases finalize "$RELEASE"` | отмечает версию как выпущенную |

**4. Удалить карты** и проверить, что их ноль. Каталог готовится к отправке
на стенды.

**5. Проверить, что Sentry действительно может расшифровать этот код.** Взять
Debug ID из главного JS-файла и спросить API Sentry `artifact-lookup`, есть
ли у него карта с таким номером. Нет — уронить пайплайн.

Зачем, если шаг 3 прошёл без ошибок: заливка может успешно уйти не в тот
проект или организацию. Эта проверка смотрит на результат с той стороны, где
он нужен.

**6. Выложить артефакт `excalidraw-app`** — тот же каталог, уже без карт.
Именно его скачивают job раскатки.

Про флаги, проверенные на этом проекте:

- **`--wait`** ждёт, пока Sentry обработает загрузку. Без него поиск сразу
  после заливки возвращал пустой список, а бандл появлялся только через
  минуту — проверка из пункта 5 давала бы ложную тревогу.
- **`set-commits --auto --ignore-missing`** без интеграции Sentry с GitHub не
  падает: пишет, что берёт коммиты из локального git, и завершается успешно.
  С интеграцией появятся ссылки на GitHub и suspect commits.
- Адрес API региона можно не заводить отдельной переменной — он
  вычисляется из DSN: `ingest.de.sentry.io` → `https://de.sentry.io`.

Используй `npx --yes @sentry/cli@3.7.0` — версия закреплена, отдельная
зависимость в `package.json` не нужна.

### 6. Раскатка

Job `deploy-staging` и `deploy-production` скачивают артефакт
`excalidraw-app`, пишут конфигурацию стенда, ещё раз проверяют отсутствие карт,
публикуют стенд и регистрируют deploy:

```bash
npx --yes @sentry/cli@3.7.0 deploys new \
  --release "<релиз>" --env staging --name staging-01
```

`--env` — класс стенда, `--name` — конкретный стенд, как `environment` и тег
`stand` в лабе 02b.

В `deploy-production` добавь **повторную заливку карт из архива**
`sentry-bundle` перед публикацией. Это та же процедура, что при
восстановлении. Выполняясь на каждой выкатке на прод, она заодно проверяет,
что архив рабочий, — узнавать это в момент инцидента поздно. Если бандл в
Sentry жив, CLI ответит `Nothing to upload` и данные повторно не передаст.

### 7. Workflow восстановления

Отдельный `restore-sourcemaps.yml`, запускаемый вручную: на входе ID прогона
и имя релиза. Скачивает `sentry-bundle` из того прогона и заливает.

Для скачивания артефакта другого прогона у `actions/download-artifact@v4`
есть `run-id` и `github-token`, а workflow нужно право `actions: read`.

### 8. Настрой подтверждение для прода

**Settings → Environments → production → Required reviewers** — добавь себя.
Галку **Prevent self-review** не ставь, иначе подтвердить собственную выкатку
не получится.

### 9. Включи Pages

После первой публикации появится ветка `gh-pages`. Тогда:

**Settings → Pages → Source: Deploy from a branch → `gh-pages` / `(root)`**

Оба workflow ниже проверены `actionlint`. Процедура заливки, проверка через
`artifact-lookup` и повторная заливка из архива прогнаны локально с тем же
`sentry-cli` 3.7.0 против настоящего Sentry.

`.github/workflows/build-and-deploy.yml`:

```yaml
name: build-and-deploy

on:
  push:
    branches: [main]

permissions:
  contents: write

env:
  SENTRY_ORG: ${{ vars.SENTRY_ORG }}
  SENTRY_PROJECT: excalidraw-lab

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      release: ${{ steps.release.outputs.name }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0 # история нужна, чтобы привязать коммиты к релизу

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: yarn

      - run: yarn install --frozen-lockfile

      - name: Имя релиза
        id: release
        run: echo "name=excalidraw-lab@$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"

      - name: Сборка артефакта
        env:
          VITE_APP_RELEASE: ${{ steps.release.outputs.name }}
        run: yarn workspace excalidraw-app build:artifact

      - name: Вшить Debug ID в код и карты
        run: npx --yes @sentry/cli@3.7.0 sourcemaps inject excalidraw-app/build

      # До заливки и до удаления карт: если заливка упадёт, архив уже есть.
      - name: Архив бандла для Sentry
        uses: actions/upload-artifact@v4
        with:
          name: sentry-bundle
          path: excalidraw-app/build
          retention-days: 90 # максимум для публичного репозитория

      - name: Релиз и заливка карт
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
          RELEASE: ${{ steps.release.outputs.name }}
        run: |
          cli="npx --yes @sentry/cli@3.7.0"
          $cli releases new "$RELEASE"
          $cli sourcemaps upload --release "$RELEASE" --wait excalidraw-app/build
          $cli releases set-commits "$RELEASE" --auto --ignore-missing
          $cli releases finalize "$RELEASE"

      - name: Убрать карты из артефакта
        run: |
          find excalidraw-app/build -name '*.map' -delete
          count=$(find excalidraw-app/build -name '*.map' | wc -l)
          echo "карт в артефакте: $count"
          test "$count" -eq 0

      - name: Карты для этого кода есть в Sentry
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
        run: |
          set -o pipefail # иначе сбой curl спрячется за успешным jq
          region=$(sed -nE 's#^VITE_SENTRY_DSN=.*ingest\.([a-z]+\.)?sentry\.io.*#https://\1sentry.io#p' .env.production)
          main=$(ls -S excalidraw-app/build/assets/index-*.js | head -1)
          id=$(grep -o '//# debugId=[a-f0-9-]*' "$main" | cut -d= -f2)
          test -n "$id" || { echo "в $main нет Debug ID"; exit 1; }
          found=$(curl -fsS -H "Authorization: Bearer $SENTRY_AUTH_TOKEN" \
            "$region/api/0/projects/$SENTRY_ORG/$SENTRY_PROJECT/artifact-lookup/?debug_id=$id" \
            | jq length)
          echo "$(basename "$main") debug_id=$id → бандлов в Sentry: $found"
          test "$found" -gt 0

      - uses: actions/upload-artifact@v4
        with:
          name: excalidraw-app
          path: excalidraw-app/build
          retention-days: 14

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4 # только ради скриптов из deploy/

      - uses: actions/download-artifact@v4
        with:
          name: excalidraw-app
          path: stand

      - name: Конфигурация стенда
        run: deploy/render-config.sh "file://$PWD/deploy/stands/staging-01.json" stand

      - name: Публикация
        env:
          PAGES_REPO_URL: https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/${{ github.repository }}.git
        run: |
          test "$(find stand -name '*.map' | wc -l)" -eq 0
          deploy/publish-pages.sh stand staging-01

      - name: Deploy в Sentry
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
        run: >
          npx --yes @sentry/cli@3.7.0 deploys new
          --release "${{ needs.build.outputs.release }}"
          --env staging
          --name staging-01
          --url "https://${{ github.repository_owner }}.github.io/${{ github.event.repository.name }}/staging-01/"

  deploy-production:
    needs: [build, deploy-staging]
    runs-on: ubuntu-latest
    environment: production # ждёт подтверждения из Required reviewers
    steps:
      - uses: actions/checkout@v4

      # Та же процедура, что при восстановлении карт. Выполняется на каждой
      # выкатке на прод, поэтому в нужный момент она точно рабочая.
      - uses: actions/download-artifact@v4
        with:
          name: sentry-bundle
          path: bundle

      - name: Повторная заливка карт из архива
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
        run: >
          npx --yes @sentry/cli@3.7.0 sourcemaps upload
          --release "${{ needs.build.outputs.release }}"
          --wait bundle

      - uses: actions/download-artifact@v4
        with:
          name: excalidraw-app
          path: stand

      - name: Конфигурация стенда
        run: deploy/render-config.sh "file://$PWD/deploy/stands/production-01.json" stand

      - name: Публикация
        env:
          PAGES_REPO_URL: https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/${{ github.repository }}.git
        run: |
          test "$(find stand -name '*.map' | wc -l)" -eq 0
          deploy/publish-pages.sh stand production-01

      - name: Deploy в Sentry
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
        run: >
          npx --yes @sentry/cli@3.7.0 deploys new
          --release "${{ needs.build.outputs.release }}"
          --env production
          --name production-01
          --url "https://${{ github.repository_owner }}.github.io/${{ github.event.repository.name }}/production-01/"
```

`.github/workflows/restore-sourcemaps.yml`:

```yaml
name: restore-sourcemaps

on:
  workflow_dispatch:
    inputs:
      run_id:
        description: ID прогона build-and-deploy, собравшего нужную версию
        required: true
      release:
        description: Имя релиза, например excalidraw-lab@a1b2c3d
        required: true

permissions:
  actions: read # скачивать артефакты другого прогона

jobs:
  restore:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: sentry-bundle
          path: bundle
          run-id: ${{ inputs.run_id }}
          github-token: ${{ secrets.GITHUB_TOKEN }}

      - name: Заливка карт из архива
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
          SENTRY_ORG: ${{ vars.SENTRY_ORG }}
          SENTRY_PROJECT: excalidraw-lab
          RELEASE: ${{ inputs.release }}
        run: npx --yes @sentry/cli@3.7.0 sourcemaps upload --release "$RELEASE" --wait bundle
```

Два job раскатки почти одинаковые. Для двух стендов это нормально, для
шестнадцати — нет: там job раскатки выносят в переиспользуемый workflow
(`workflow_call`) с параметрами «стенд» и «окружение».

</details>

## Проверка

```bash
git push origin main
```

**1. Сборка.** В логе job `build`:

- шаг заливки — `Bundle ID: …` и `File processing complete`;
- шаг «Карты для этого кода есть в Sentry» —
  `index-….js debug_id=… → бандлов в Sentry: 1`;
- на странице прогона — два артефакта: `sentry-bundle` и `excalidraw-app`.

**2. Staging.** `deploy-staging` пройдёт, `deploy-production` остановится с
пометкой «Waiting for review». Открой
`https://<логин>.github.io/sentry-practice/staging-01/` и нажми детонатор 1:
событие с окружением `staging`, тегом `stand: staging-01` и **читаемым
стектрейсом**.

**3. Релиз.** В Sentry **Releases → excalidraw-lab@<хеш>**: один deploy в
`staging` и список коммитов.

**4. Прод.** В Actions: **Review deployments → Approve**. В логе
`deploy-production`, в шаге повторной заливки — `Nothing to upload, all files
are on the server`: архив сошёлся с тем, что уже в Sentry. На странице релиза
теперь два deploy.

**5. Восстановление.** ID прогона — в адресе его страницы
(`…/actions/runs/<id>`):

gh run watch
```

В логе снова `Nothing to upload`: бандл жив. Настоящее восстановление выглядит
так же, только вместо этой строки будет `Uploaded files to Sentry`.

done
```

Совпадут. А `config.js` у стендов разный.

## Что должно сломаться, если сделать неправильно

| Симптом | Причина |
|---|---|
| Белая страница, 404 на ассеты | `base` не относительный |
| Шрифты 403 с адреса CDN | Поставил абсолютный `base` — см. пункт 3 |
| `в …/index-….js нет Debug ID` | Нет шага `inject`, или плагин ещё подключён: у сборки плагином нет комментария `//# debugId=` |
| `бандлов в Sentry: 0` | Заливка ушла не в тот проект или организацию: сверь `SENTRY_ORG` и `SENTRY_PROJECT` |
| `Could not resolve host: de.sentry.io` | Сетевой сбой. Перезапусти job — архив к этому моменту уже сохранён |
| Шаг «Публикация» падает на проверке карт | В job раскатки скачан `sentry-bundle`, а не `excalidraw-app` |
| `deploys new` падает с ошибкой про релиз | Не выполнился `releases new` в job `build` |
| `restore-sourcemaps`: `Artifact 'sentry-bundle' not found` | Неверный `run_id` или архив удалён по сроку хранения |
| `restore-sourcemaps`: ошибка доступа при скачивании архива | Проверь `permissions: actions: read` в этом workflow |
| `Permission denied` при публикации | Нет `permissions: contents: write` |
| `! [rejected] gh-pages -> gh-pages (fetch first)` при публикации | Два прогона публиковали одновременно. Перезапусти job |
| Стенд по адресу без слэша на конце грузит чужой `config.js` | Путь `./config.js` отсчитывается от URL страницы. Pages сам добавляет слэш редиректом; на своём веб-сервере проверь, что редирект есть |
| `deploy-production` не ждёт подтверждения | В окружении `production` не заданы Required reviewers |
| Suspect commits пустые | Нет `fetch-depth: 0` или не установлена интеграция с GitHub |
| 404 на всём сайте | Pages не включены или выбрана не та ветка |
