# Лаба 07. CI: собрать один раз, раскатить на стенды

**~50 минут**

## Цель

Построить пайплайн, в котором артефакт собирается один раз, а затем без
изменений уезжает на staging и — после ручного подтверждения — на прод.
Токен живёт только в секретах CI, а Sentry знает, какой релиз когда и на какой
стенд выкатили.

## Теория

### Форма пайплайна

```
build ──► artifact ──► deploy staging-01 ──► [подтверждение] ──► deploy production-01
  │                          │                                          │
  ├ релиз                    ├ config.js стенда                         ├ config.js стенда
  ├ заливка карт             ├ публикация                               ├ публикация
  └ проверка: карт нет       └ deploy в Sentry                          └ deploy в Sentry
```

Всё, что относится к артефакту, происходит **один раз** в `build`: имя
релиза, заливка карт, привязка коммитов. Всё, что относится к стенду, — в
job раскатки: конфигурация, публикация, регистрация deploy.

### Релиз и deploy — разные вещи

- **Релиз** — версия кода. Создаётся при сборке, один на артефакт.
- **Deploy** — факт выкатки релиза в окружение в определённый момент. Их
  столько, сколько было раскаток.

На странице релиза в Sentry видно, куда и когда его выкатывали. Если после
выкатки на прод посыпались ошибки, по времени deploy это сразу видно.

Плагин Vite умеет создавать deploy сам, но в модели «одна сборка — много
стендов» это неверно: при сборке ещё неизвестно, куда артефакт поедет.
Поэтому deploy регистрирует шаг раскатки через `sentry-cli`.

### Как это соотносится с рабочим проектом

| В практикуме | На рабочем проекте |
|---|---|
| job `deploy-*` | выкатка контейнера в под |
| `deploy/render-config.sh` в job | entrypoint контейнера |
| подкаталог стенда на Pages | под стенда |
| `deploy/stands/*.json` | внутренний сервис конфигурации |

## Что уже есть в репозитории

- `deploy/publish-pages.sh <каталог> <стенд>` — публикует стенд в ветку
  `gh-pages`: заменяет только подкаталог этого стенда, остальные не трогает.
  Проверен на локальном репозитории: первая публикация, соседний стенд,
  повтор без изменений, удаление устаревших файлов, ошибка доступа.

## Задание

### 1. Заведи репозиторий и залей код

```bash
gh repo create sentry-practice --public --source=. --remote=origin --push
```

### 2. Секрет и переменная

```bash
gh secret set SENTRY_AUTH_TOKEN
gh variable set SENTRY_ORG --body "<слаг организации>"
```

Токен — секрет: GitHub маскирует его в логах и не показывает после записи.
Слаг организации секретом не является, поэтому это обычная переменная.
Различать эти две вещи полезно и в рабочем проекте.

### 3. Разберись с путями — тут ловушка

Pages отдаёт сайт с `https://<логин>.github.io/sentry-practice/`, а стенды
будут жить глубже — в `staging-01/` и `production-01/`. Сборка Vite по
умолчанию рассчитана на корень домена, и по такому адресу все ассеты уйдут в
404.

Напрашивается `base: "/sentry-practice/staging-01/"`. **Так делать не надо**,
и дело даже не в том, что сборка одна на все стенды. Excalidraw подставляет
путь ассета в адрес своего CDN шрифтов, срезая ведущий слэш, и получается:

```
https://excalidraw.nyc3.cdn.digitaloceanspaces.com/oss/sentry-practice/fonts/... → 403
```

Рабочий вариант — **относительный** `base`. Тогда ассеты адресуются от текущего
каталога, и одна сборка работает на любой глубине. В
`excalidraw-app/package.json` не зря стоит `"homepage": "."` — авторы имели в
виду ровно это, просто Vite, в отличие от CRA, это поле не читает.

Добавь `base` в `excalidraw-app/vite.config.mts`.

### 4. Не трогай `setCommits`

Привязка коммитов к релизу у плагина **уже включена** по умолчанию:
`{ auto: true, ignoreMissing: true, ignoreEmpty: true }`, и неудача при этом
не роняет сборку.

Если задать `setCommits` явно, пусть даже с теми же значениями, это поведение
пропадёт: проверено по коду плагина 5.4.0. Тогда без интеграции Sentry с
GitHub привязка коммитов упадёт, а `errorHandler` из лабы 04 уронит всю сборку.

Нужно две вещи:

- `fetch-depth: 0` в checkout — иначе в CI нет истории коммитов;
- интеграция **Settings → Integrations → GitHub** в Sentry — иначе коммиты
  подтянутся без ссылок на GitHub и без suspect commits.

### 5. Напиши workflow

Требования:

- запускается при пуше в `main`;
- job `build` собирает артефакт **один раз**, проверяет, что в нём нет ни
  одного `.map`, и выкладывает его через `actions/upload-artifact`;
- job `deploy-staging` скачивает **тот же** артефакт, пишет в него
  конфигурацию `staging-01`, публикует и регистрирует deploy в Sentry;
- job `deploy-production` делает то же для `production-01`, но только после
  staging и после ручного подтверждения;
- артефакт в job раскатки не пересобирается.

Регистрация deploy:

```bash
npx --yes @sentry/cli@3.7.0 deploys new \
  --org "<слаг>" --release "<релиз>" --env staging --name staging-01
```

`--env` — класс стенда, `--name` — конкретный стенд. Ровно то же разделение,
что `environment` и тег `stand` в лабе 02b.

### 6. Настрой подтверждение для прода

**Settings → Environments → production → Required reviewers** — добавь себя.
Галку **Prevent self-review** не ставь, иначе подтвердить собственную выкатку
не получится.

Окружение `production` в GitHub появится после первого прогона workflow,
либо создай его заранее той же кнопкой.

### 7. Включи Pages

После первой публикации появится ветка `gh-pages`. Тогда:

**Settings → Pages → Source: Deploy from a branch → `gh-pages` / `(root)`**

### 8. Убери токен с ноутбука

Ради этого всё и затевалось:

```bash
rm excalidraw-app/.env.sentry-build-plugin
```

Локальная сборка теперь честно скажет `No auth token provided` — и это
правильно. Артефакты собирает CI.

<details>
<summary>Эталон</summary>

`excalidraw-app/vite.config.mts`, в начало возвращаемого объекта:

```ts
    // Относительные пути: одна сборка работает на любой глубине. Абсолютный
    // base ломает адреса CDN-шрифтов Excalidraw.
    base: "./",
```

`.github/workflows/build-and-deploy.yml`:

```yaml
name: build-and-deploy

on:
  push:
    branches: [main]

permissions:
  contents: write

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      release: ${{ steps.release.outputs.name }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0 # история нужна, чтобы привязать коммиты к релизу

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: yarn

      - run: yarn install --frozen-lockfile

      - name: Имя релиза
        id: release
        run: echo "name=excalidraw-lab@$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"

      - name: Сборка артефакта и заливка карт
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
          VITE_APP_RELEASE: ${{ steps.release.outputs.name }}
        run: yarn workspace excalidraw-app build:artifact

      - name: Карт в артефакте быть не должно
        run: |
          count=$(find excalidraw-app/build -name '*.map' | wc -l)
          echo "карт в сборке: $count"
          test "$count" -eq 0

      - uses: actions/upload-artifact@v4
        with:
          name: excalidraw-app
          path: excalidraw-app/build
          retention-days: 14

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4 # только ради скриптов из deploy/

      - uses: actions/download-artifact@v4
        with:
          name: excalidraw-app
          path: stand

      - name: Конфигурация стенда
        run: deploy/render-config.sh "file://$PWD/deploy/stands/staging-01.json" stand

      - name: Публикация
        env:
          PAGES_REPO_URL: https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/${{ github.repository }}.git
        run: deploy/publish-pages.sh stand staging-01

      - name: Deploy в Sentry
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
        run: >
          npx --yes @sentry/cli@3.7.0 deploys new
          --org "${{ vars.SENTRY_ORG }}"
          --release "${{ needs.build.outputs.release }}"
          --env staging
          --name staging-01
          --url "https://${{ github.repository_owner }}.github.io/${{ github.event.repository.name }}/staging-01/"

  deploy-production:
    needs: [build, deploy-staging]
    runs-on: ubuntu-latest
    environment: production # ждёт подтверждения из Required reviewers
    steps:
      - uses: actions/checkout@v4

      - uses: actions/download-artifact@v4
        with:
          name: excalidraw-app
          path: stand

      - name: Конфигурация стенда
        run: deploy/render-config.sh "file://$PWD/deploy/stands/production-01.json" stand

      - name: Публикация
        env:
          PAGES_REPO_URL: https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/${{ github.repository }}.git
        run: deploy/publish-pages.sh stand production-01

      - name: Deploy в Sentry
        env:
          SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
        run: >
          npx --yes @sentry/cli@3.7.0 deploys new
          --org "${{ vars.SENTRY_ORG }}"
          --release "${{ needs.build.outputs.release }}"
          --env production
          --name production-01
          --url "https://${{ github.repository_owner }}.github.io/${{ github.event.repository.name }}/production-01/"
```

Два job раскатки почти одинаковые. Для двух стендов это нормально, для
шестнадцати — нет: там job раскатки выносят в переиспользуемый workflow
(`workflow_call`) с параметрами «стенд» и «окружение».

</details>

## Проверка

```bash
git push origin main
```

**1. Сборка и staging.** В Actions пройдут `build` и `deploy-staging`, а
`deploy-production` остановится с пометкой «Waiting for review».

Открой `https://<логин>.github.io/sentry-practice/staging-01/` и разверни
панель: `mode: production`, `stand: staging-01`, `release: excalidraw-lab@<хеш>`.
Нажми детонатор 1 — в Sentry событие с окружением `staging`, тегом
`stand: staging-01` и читаемым стектрейсом.

**2. Релиз и deploy.** В Sentry открой **Releases → excalidraw-lab@<хеш>**.
Там один deploy — в `staging`. Если интеграция с GitHub установлена, там же
будут коммиты.

**3. Подтверждение и прод.** В Actions нажми **Review deployments → Approve**.
После выкатки открой `.../sentry-practice/production-01/`: тот же релиз,
`stand: production-01`. На странице релиза в Sentry теперь два deploy.

**4. Артефакт один.** Имена чанков содержат хеш содержимого, так что
сравнить их — значит сравнить код:

```bash
for s in staging-01 production-01; do
  curl -s "https://<логин>.github.io/sentry-practice/$s/" | grep -o 'assets/index-[^"]*\.js' | head -1
done
```

Имена совпадут. А `config.js` у стендов разный:

```bash
curl -s https://<логин>.github.io/sentry-practice/staging-01/config.js
curl -s https://<логин>.github.io/sentry-practice/production-01/config.js
```

**5. Карты закрыты.**

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  https://<логин>.github.io/sentry-practice/production-01/sw.js.map
```

`404`. Карт снаружи нет, а стектрейсы читаемые.

## Что должно сломаться, если сделать неправильно

| Симптом | Причина |
|---|---|
| Белая страница, 404 на ассеты | `base` не относительный |
| Шрифты 403 с адреса CDN | Поставил абсолютный `base` — см. пункт 3 |
| `build` падает на привязке коммитов | Задал `setCommits` явно — убери, см. пункт 4 |
| Шаг «Карт в артефакте быть не должно» падает | Заливка не прошла или в сборке остались карты сервис-воркера (лаба 05) |
| `deploys new`: релиз не найден | `build` не создал релиз: проверь, что в плагине задан `release.name` (лаба 04), и слаг в `SENTRY_ORG` |
| `Permission denied` при публикации | Нет `permissions: contents: write` |
| `! [rejected] gh-pages -> gh-pages (fetch first)` при публикации | Два прогона публиковали одновременно. Перезапусти job |
| Стенд по адресу без слэша на конце грузит чужой `config.js` | Путь `./config.js` отсчитывается от URL страницы. Pages сам добавляет слэш редиректом; на своём nginx проверь, что редирект есть |
| `deploy-production` не ждёт подтверждения | В окружении `production` не заданы Required reviewers |
| Suspect commits пустые | Нет `fetch-depth: 0` или не установлена интеграция с GitHub |
| 404 на всём сайте | Pages не включены или выбрана не та ветка |

## Итог

- [ ] Репозиторий на GitHub, токен в секретах, слаг в переменных
- [ ] Артефакт собирается один раз и проверяется на отсутствие карт
- [ ] Тот же артефакт раскатывается на staging и после подтверждения на прод
- [ ] На странице релиза в Sentry видны оба deploy
- [ ] Токена на ноутбуке больше нет
