# План практикума (облегчённый цикл)

Документ фиксирует принятые решения и результаты проверок. Заменяет собой
полный цикл OpenSpec из `CLAUDE.md` — по договорённости с заказчиком практикума.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Формат | Пошаговые лабы, руками делает обучаемый | Конфигурацию Sentry надо один раз написать самому |
| База | Excalidraw (Vite 5, React 19, TS, yarn workspaces) | Реальный прод-проект, большой минифицированный бандл, работает без бэкенда |
| Sentry | sentry.io, бесплатный тариф | Самохостинг — отдельная лаба на 40 минут до начала темы |
| Стенды | Локально, затем те же шаги в GitHub Actions | Смысл «токен только в CI» иначе остаётся теорией |
| Модель сборки | Один артефакт на все стенды; окружение из `config.js`, который пишет стенд (с лабы 02b) | Так устроен рабочий проект обучаемого: 16+ стендов, протестированный артефакт не меняется, конфигурация приходит при старте контейнера |
| Окружения в Sentry | `environment` — класс стенда, тег `stand` — конкретный стенд | Алерты и фильтры рассчитаны на несколько окружений, а не на десятки |
| Deploy в Sentry | Регистрирует job раскатки через `sentry-cli`, не сборка | При сборке неизвестно, куда поедет артефакт |
| Мониторинг в коде | Фасад `excalidraw-app/monitoring/`, SDK только в адаптере, запрет импорта `@sentry/*` в линтере (лаба 09) | Бизнес-ошибки разнесут вызовы SDK по всему коду; у Excalidraw уже есть такой же фасад для `jotai` |
| Бизнес-ошибки | Четыре класса: баг, аномалия, обработанный сбой, ожидаемый исход; у проблем стабильный код и `fingerprint`; ожидаемые исходы — крошки | Ожидаемые исходы в issues — шум; без `fingerprint` Sentry группирует по стектрейсу и игнорирует код |
| Заливка карт в CI | `sentry-cli` 3.7.0 вместо плагина: `inject` → архив → `upload --wait` → удаление → проверка через `artifact-lookup`; повторная заливка при выкатке на прод и workflow восстановления (лаба 07) | Карты после плагина нельзя заархивировать и залить повторно; Sentry удаляет бандл после 90 дней без использования |
| Хостинг | Публичный репозиторий + GitHub Pages | Бесплатно, `gh` уже авторизован |
| Существующий `sentry.ts` | Снести в лабе 00, написать заново, сравнить в лабе 08 | И практика письма, и разбор чужих решений |

## Что проверено на живых сборках

Не взято из документации, а выполнено и подтверждено:

- Excalidraw собирается на Node 26.7.0 + yarn 1.22.22 (`yarn install` 5,5 мин,
  сборка 12 с).
- Стартовое состояние: `sourcemap: true`, 115 `.map` в сборке, комментарий
  `//# sourceMappingURL` на месте, карты отдаются по HTTP с кодом 200.
- `import.meta.env.MODE` при `--mode staging` компилируется в `"staging"`,
  а `PROD` — в `true`. **`PROD` не отличает staging от production.**
- `sourcemap: "hidden"` убирает комментарий; плагин вшивает
  `sentry-dbid-<uuid>` и в бандл, и в карту.
- Плагин читает `.env.sentry-build-plugin` из каталога сборки
  (`excalidraw-app/`), а не из корня репозитория.
- **Без токена сборка не падает** — только предупреждение.
- **При провале заливки карты всё равно удаляются, код возврата остаётся 0.**
  Лечится `errorHandler`, который пробрасывает ошибку: проверено, сборка
  честно падает с кодом 1.
- `vite-plugin-pwa` создаёт `sw.js.map` и `workbox-*.js.map` **после** плагина
  Sentry, поэтому они переживают удаление и отдаются наружу с кодом 200.
  Закрывается через `workbox: { sourcemap: false }` — после этого в сборке
  ноль карт.
- Абсолютный `base: "/sentry-practice/"` ломает CDN-шрифты Excalidraw
  (403: путь стенда попадает внутрь адреса CDN). Относительный `base: "./"`
  работает: под подпутём ноль ошибок в консоли.
- Без `Sentry.init` вызов `captureException` в `TopErrorBoundary` — тихий
  no-op, приложение не падает.

### Одна сборка — много стендов (лабы 02b, 07)

Проверено с локальной заглушкой ingest, которая записывала конверты SDK:

- Синхронный `<script src="./config.js">` в `<head>` сохраняется в собранном
  `index.html` и стоит раньше модульного бандла. Vite выводит предупреждение
  `can't be bundled without type="module"` — ожидаемо. С `type="module"`
  сборка падает: `Could not resolve "./config.js" from "index.html"`.
- Один артефакт на двух стендах: побайтово одинаковый бандл, события пришли с
  `environment: staging, stand: staging-01` и
  `environment: production, stand: production-01`.
- Стенд без `config.js`: приложение работает, 404 в консоли, события приходят
  с `environment: unconfigured`.
- Дев-сервер Vite на запрос браузера к несуществующему `config.js` отвечает
  404. Запрос curl без `Sec-Fetch-Dest: script` получает `index.html`.
- `global.d.ts` у Excalidraw — модуль, глобальные типы расширяются только
  через `declare global`.
- `deploy/publish-pages.sh` проверен на локальном bare-репозитории: создание
  ветки, соседний стенд, повтор без изменений, удаление устаревших файлов,
  ошибка доступа не маскируется.
- `sentry-cli` 3.7.0: `deploys new --release --env --name --url --org`.
- По коду `@sentry/bundler-plugins` (зависимость плагина 5.4.0):
  - без `release.name` релиз называется `SENTRY_RELEASE`, либо переменными CI
    (`GITHUB_SHA` и др.), либо `git rev-parse HEAD`;
  - `setCommits` по умолчанию `{ auto, ignoreMissing, ignoreEmpty }` с
    внутренним `shouldNotThrowOnFailure`. Явно заданный `setCommits` этот флаг
    теряет, и неудача роняет сборку вместе с `errorHandler`;
  - deploy плагин создаёт сам только на Vercel (`VERCEL` и
    `VERCEL_TARGET_ENV`).
- `Sentry.ErrorBoundary` вокруг панели ловит ошибку рендера и оставляет
  приложение живым.

### Фасад и бизнес-ошибки (лаба 09)

Проверено на сборке с поддельным бэкендом сцен и заглушкой вместо Sentry:

- На исходном коде ответ бэкенда 500 показывает пользователю сообщение, а в
  Sentry не приходит ничего. Мусор вместо сцены не показывает пользователю
  ничего, а в Sentry приходит `OperationError: No error message`,
  необработанный. Причина — `return legacy_decodeFromBackend(...)` без `await`
  внутри `try` асинхронной функции.
- Эталон: 404, нет сети и ключ не той длины — событий нет, только крошки
  `outcome`; 500 и 503 — `warning` с одним `fingerprint` и совпадающими до
  кадра стектрейсами; мусор — `error` с причиной `OperationError`, сообщение
  пользователю показывается; ошибка рендера — ровно одно событие со стеком
  компонентов.
- Правило `no-restricted-imports` с `paths` и `patterns` запрещает `@sentry/*`
  (включая типовой импорт из `@sentry/core`) и сохраняет запрет на `jotai`.
  На текущем коде оно указывает на `App.tsx`, `TopErrorBoundary.tsx`,
  `sentry.ts` и архив `docs/upstream/`; `vite.config.mts` линтер не проверяет.
- По исходнику React 19.0.0: `onCaughtError` вызывается раньше
  `componentDidCatch`; заданный обработчик заменяет стандартный
  `console.error`. По исходнику `@sentry/react`: `reactErrorHandler` без
  колбэка помечает ошибку необработанной, с колбэком — обработанной.
- Переменная `VITE_APP_BACKEND_V2_GET_URL` из окружения при сборке важнее
  значения из `.env.production`.
- Группировка в интерфейсе Sentry не проверялась: события не отправлялись в
  проект обучаемого. Вывод о слипании разных кодов из одной строки без
  `fingerprint` опирается на документацию и совпадение стектрейсов.

## Известные особенности

- **Баг Excalidraw:** любая ошибка рендера под `TopErrorBoundary` даёт пустой
  экран вместо экрана ошибки — фолбэк использует `Trans`/`t()`, которым нужен
  jotai-`Provider`, отрисованный внутри самой границы
  (`Missing Provider from createIsolation`). Обходится в лабе 01.
- При относительном `base` в `manifest.webmanifest` остаётся `start_url: "/"`.
  На мониторинг не влияет, установку PWA по подпути — портит.

## Чего проверить не удалось

- Workflow из лабы 07 целиком не прогонялся на runner'е: нужен репозиторий
  обучаемого. Проверено: оба workflow проходят `actionlint` 1.7.7 (на
  контрольной поломке он ловит неверный вход действия); команды `sentry-cli`
  3.7.0 (`inject`, `upload --wait`, `releases new/set-commits/finalize`)
  прогнаны против настоящего Sentry; шаг `artifact-lookup` — на залитом,
  незалитом и собранном плагином коде; повторная заливка из архива даёт тот
  же Bundle ID; SDK в браузере отправляет Debug ID от CLI 3.7.0; входы
  `run-id`/`github-token` у `download-artifact@v4`, `jq` в образе
  `ubuntu-latest`, сроки хранения и доступ к артефактам — по исходникам и
  документации GitHub. Локально проверены все шаги, которые от них не
  зависят: сборка, относительный `base`, проверка отсутствия карт,
  `render-config.sh`, `publish-pages.sh`, синтаксис `sentry-cli`. YAML
  разбирается парсером, но зелёного прогона на runner'е не было.
- Сессии (release health) в заглушку ingest не пришли — ни без `release`, ни с
  ним. Поэтому в лабе 02b недостаток варианта с `beforeSend` описан только на
  уровне документированного: хук обрабатывает события ошибок, остальное
  сохраняет окружение из `init`.
- Отправка трейсов при загрузке страницы (проверка 5 в лабе 06) описана по
  известному поведению `browserTracingIntegration`, локально не наблюдалась.

## Устаревшее знание, которое практикум исправляет

Распространённое утверждение «`release` в SDK обязан совпадать с релизом
заливки, иначе карты не сматчатся» больше не верно. Сопоставление идёт по
Debug ID; документация Sentry прямо пишет, что создавать релиз не требуется, и
предупреждает, что привязка к `release`/`dist` делает загрузку строже. Разбор —
в лабе 03.
